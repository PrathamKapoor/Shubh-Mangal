# Site source and synthetic startup

A source bundle identifies the layout, public assets, provenance and seed amenities. `SITE_SOURCE_CONFIG` selects a JSON bundle; omission selects the original source. Seed an alternate only into an isolated database. Startup checks the database source markers and, for the synthetic fixture, requires the exact seeded layout revision. Unmarked historical revisions remain compatible only with the original source. Do not point these tests or seed commands at an existing user database.

Normal alternate startup is currently restricted to the exact `tests/fixtures/second-site/source.json` synthetic fixture. This is not general operator-configurable second-site support. The fixture uses UTM 32N and is illustrative, not field evidence or release approval. A different source is rejected by the startup guard.

The Vite build embeds a digest of the complete validated source configuration and raw layout revision and writes `site-build.json` beside its output. For production or synthetic startup, the API checks that manifest before opening the database. Build and start with the same `SITE_SOURCE_CONFIG` and `SITE_BUILD_DIR`; absent a directory, both use `dist`. The browser checks the public source digest against its build before accepting live state. For the synthetic fixture, an explicit `SITE_NAME` must match the configured source name. A mismatched, missing or stale build fails closed.

For isolated local synthetic verification, `node node_modules/@playwright/test/cli.js test -c playwright.site-b.config.js --reporter=list` builds into a fresh temporary directory, seeds a new temporary database, launches the normal `server/start.mjs`, and starts a fixture-configured Vite server. It uses synthetic users and data. It must not be used as a production deployment procedure. The separate `node --test tests/site-build.test.mjs tests/site-startup.test.mjs tests/site-source.test.mjs` checks identity and source guards.

The original-site build retains its labelled offline reference drawing. An alternate build does not fall back to it when the API is unavailable. Production and development frontends must be built or started with the same source config as their API. A Vite development server is a separate process and must receive `SITE_SOURCE_CONFIG` itself; its browser rejects a reachable API with a different build identity.

For alternate CSV identity import, provide a `sourceDocument` column identifying the reviewed evidence. The original site retains its historical PDF default. Review, publication, directions, live provider, field alignment, source rights and recovery requirements remain independent of a synthetic test.

For an alternate production build, only source assets declared by the selected bundle and the generic owner CSV templates are copied into the build output. Original-site source downloads, drawings and artwork are not automatically copied. Selected asset paths must resolve inside `public/`; symlinks escaping that directory are rejected. The original-site build retains its existing public assets. This packaging isolation does not remove the fixture-only startup restriction.
