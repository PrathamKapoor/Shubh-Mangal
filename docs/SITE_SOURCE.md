# Site source and synthetic startup

A source bundle identifies the layout, public assets, provenance and seed amenities. `SITE_SOURCE_CONFIG` selects a JSON bundle; omission selects the original source. Seed an alternate only into an isolated database. Startup checks the database source markers and, for alternate sources, requires the exact seeded layout revision. Unmarked historical revisions remain compatible only with the original source. Do not point these tests or seed commands at an existing user database.

Normal alternate startup accepts validated source bundles without matching a fixture identity. Supply a project-relative layoutFile, declared WGS84 UTM projection metadata, bounds, unique geometry IDs and selected public asset paths. Startup still requires a matching browser build and an independently initialized database tied to the selected layout revision. The example fixture uses UTM 32N and remains illustrative.

The Vite build embeds a digest of the complete validated source configuration and raw layout revision and writes `site-build.json` beside its output. For production or synthetic startup, the API checks that manifest before opening the database. Build and start with the same `SITE_SOURCE_CONFIG` and `SITE_BUILD_DIR`; absent a directory, both use `dist`. The browser checks the public source digest against its build before accepting live state. For an alternate source, an explicit `SITE_NAME` must match the configured source name. A mismatched, missing or stale build fails closed.

For isolated local synthetic verification, `node node_modules/@playwright/test/cli.js test -c playwright.site-b.config.js --reporter=list` builds into a fresh temporary directory, seeds a new temporary database, launches the normal `server/start.mjs`, and starts a fixture-configured Vite server. It uses synthetic users and data. It must not be used as a production deployment procedure. The separate `node --test tests/site-build.test.mjs tests/site-startup.test.mjs tests/site-source.test.mjs` checks identity and source guards.

The original-site build retains its labelled offline reference drawing. An alternate build does not fall back to it when the API is unavailable. Production and development frontends must be built or started with the same source config as their API. A Vite development server is a separate process and must receive `SITE_SOURCE_CONFIG` itself; its browser rejects a reachable API with a different build identity.

For alternate CSV identity import, provide a `sourceDocument` column identifying the reviewed evidence. The original site retains its historical PDF default. Review, publication, directions, live provider, field alignment, source rights and recovery requirements remain independent of a synthetic test.

For an alternate production build, only source assets declared by the selected bundle and the generic owner CSV templates are copied into the build output. Original-site source downloads, drawings and artwork are not automatically copied. Selected asset paths must resolve inside `public/`; symlinks escaping that directory are rejected. The original-site build retains its existing public assets. Legacy area IDs and road decoration are enabled only for the original source; alternate renderers use area kinds such as site, road and amenity. Amenity coordinates are checked against the selected geographic bounds; the original source retains its historical placement envelope for compatibility.

For a new deployment, set SITE_SOURCE_CONFIG and an isolated LOCAL_DB_PATH/MEDIA_DIRECTORY, run npm run db:migrate and npm run db:seed once, build with npm run build, provision the owner with npm run db:owner, then run npm start with the same source/build settings. Production additionally requires PostgreSQL and the HTTPS configuration in DEPLOYMENT.md. A populated database cannot be switched to a different source bundle.
